Un portfolio técnico tiene pocos segundos para explicar quién eres, qué sabes hacer y por qué merece la pena revisar tu trabajo. El objetivo era comunicar todo eso con una experiencia propia, sin recurrir a una plantilla genérica ni a una lista interminable de tecnologías.

La propia aplicación debía funcionar como evidencia del nivel de frontend: arquitectura, responsive, testing, accesibilidad y atención al detalle.

Accesibilidad en el comportamiento

  • Landmarks semánticos, listas y metadatos con dl/dt/dd.
  • Skip-link al contenido principal y focus-visible global.
  • Menú con aria-expanded y aria-controls; Escape cierra el panel y devuelve el foco.
  • Decoraciones con aria-hidden y movimiento reducido mediante prefers-reduced-motion.

Son medidas implementadas, no una certificación de accesibilidad. La revisión manual con teclado sigue siendo parte del trabajo.

Sin librerías UI ni de iconos: los visuals se construyen con HTML y CSS. La UI compartida evita duplicación y las rutas secundarias se cargan bajo demanda.

PROBLEMA → DIAGNÓSTICO → SOLUCIÓN

ProjectCard y el budget de CSS

Durante el desarrollo, el SCSS de ProjectCard superó el umbral de aviso de 4 kB: aproximadamente 4,5 kB. Se eliminaron estilos duplicados, se consolidaron media queries y reglas compartidas y se reutilizó la tipografía global para bajar de 4 kB.

El estado actual mantiene esa consolidación. La comprobación relevante es el CSS compilado en producción, no el peso del archivo SCSS fuente.

Los budgets permanecen en angular.json: 1 MB y 8 kB son los límites de error respectivos. El objetivo es resolver los avisos antes de llegar a ellos.

Vitest / Angular unit-test builder · jsdom

Los tests se centran en comportamiento y contenido relevante, evitando depender de detalles visuales de CSS que harían la suite innecesariamente frágil.

  • Routing: Home, catálogo, case study, placeholders y 404.
  • Navegación: anchors a proyectos y contacto, enlaces de CV y repositorio.
  • Contenido: estado y stack de proyectos, experiencia y orden de las secciones.
  • Interacción: apertura del menú móvil, cierre con Escape y restauración del foco.

No se publica un porcentaje de cobertura ni un contador fijo: el resultado vigente se obtiene ejecutando npm test -- --watch=false.

01 / CSS budget

ProjectCard combina contenido y visual. Reducir duplicación permitió conservar ambos dentro del budget, sin elevar el límite del proyecto.

02 / Densidad responsive

Experience y Tech Stack concentran mucha información. La jerarquía, los layouts adaptativos, el wrapping de chips y una timeline móvil simplificada ayudan a mantener la lectura.

03 / Evitar sobrearquitectura

Los datos estáticos siguen siendo arrays readonly. Signals se reservan para estado, como el menú móvil, o parámetros reactivos de ruta; no para convertir todo el contenido en estado mutable.

Trade-offs

SIN UI LIBRARY

Control visual y menos dependencias a cambio de mantener más CSS propio.

SIN SSR TODAVÍA

Se priorizó completar producto y experiencia antes de añadir SSR/prerender. SEO avanzado queda para una iteración posterior.

Una Home completa conecta perfil, stack, proyectos, experiencia y contacto, con acceso al CV. Este case study añade profundidad técnica sin cargarla toda en la página de inicio.

El build comprueba budgets y la suite verifica comportamiento. No se atribuyen métricas de negocio ni resultados de Lighthouse que no se hayan medido.

  1. 01 / Diseñar sistema antes que páginas

    Definir tokens y componentes antes de construir las secciones me permitió ajustar la identidad visual desde una base común, en lugar de corregir cada bloque por separado.

  2. 02 / La jerarquía importa tanto como el contenido

    En móvil tuve que decidir qué se lee primero. Cambiar columnas no basta cuando experiencia y tecnologías compiten por la atención.

  3. 03 / La calidad se construye durante todo el proceso

    Los tests de navegación, los estados accesibles y los budgets introducen límites concretos mientras construyo, no solo al terminar.
